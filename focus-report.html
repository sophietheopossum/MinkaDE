Tarnished Focus

Two focus defects behind Keeper's SSH prompt landing under a blank window — and why the obvious fix for each one doesn't work.

A · The stacking race

Keeper opens two toplevels from one process over two separate wl_display connections. The blank helper is created first; the real dialog 16 ms later, and only the dialog ever sends an activation request.

09:17:10.255839  new xdg toplevel  0xb  keeper-password-manager   blank helper, first
09:17:10.271885  new xdg toplevel  0xc  keeperpasswordmanager     the dialog, +16 ms
09:17:10.275520  activate request  0xc  XdgActivation             only the dialog

Every rule in the config says the dialog should win: it's created later and onOpen adds at "front"; it's the only one activated; and onFocus raises unconditionally. It loses roughly four times in five.

Why

An onOpen focus isn't applied when it's issued. It's queued into pending_initial_focus_window_ids and replayed when the window first reaches a rendered frame. The replay is six lines with no staleness check, and it's drained last-write-wins:

state.rs:3623   sorted_windows_top_to_bottom → right_z.cmp(&left_z)   DESCENDING z
tty.rs:5634     push onto the drain vector, inside that render walk
tty.rs:6925     drain in push order → apply_pending_initial_focus_for_window
input.rs:2730   remove from set, then focus_window — unconditionally

So whichever window is drained last takes the keyboard, and via the isFocused snapshot diff the config then raises it. Nothing in that chain asks which window the user needs.

The measurement that broke my first theory eDP-1 runs at 60049 mHz — a 16.65 ms frame — and the two toplevels are created 16.05 ms apart. Same-frame readiness is therefore only ~3.6% likely, so the z-descending order can't be the dominant path. What fits the observed ~20% success rate is that the blank helper usually reaches its first rendered frame later than the dialog despite being created earlier. Both routes hand the win to the helper; only the timing differs.

Why all three patches failed

  • Minimal Rust guard — replay the queued focus only if the window is still the focus owner. Compiles clean, anchors verified, elegantly time-free. But it makes the other observed variant strictly worse: when Keeper activates the helper 4.7 ms after the dialog, the owner legitimately is the helper, so the dialog's replay gets dropped and it never gets focus at all. It also removes the only self-heal for a stranded deferred hand-off.
  • Config-only burst guard — refuse to raise a window above a sibling that opened after it. Typechecks, but corrects z-order only: the keyboard still goes to the helper. It also scans the global stack without filtering by workspace, so a window opening on the ScreenPad can act as a spurious blocker, and it fails the same 4.7 ms variant.
  • Full focus-provenance system — priorities, generations, a real deferred queue. Rejected: a session-lock path lets a window behind the lock screen take keyboard focus, and any pointer click within the grace window suppresses a legitimately-opening dialog.

The tension is real rather than an implementation slip. In one variant Keeper explicitly asks for the helper last; in the other it never asks at all. Honouring client intent gives the wrong answer in the first case, and ignoring it gives the wrong answer in the second. The rule that satisfies both is prefer the later-created window of an open burst — which no candidate implemented cleanly.

B · The jump to the Vault

Authorising closes both prompt windows and focus lands on the pre-existing maximised Keeper Vault instead of returning to rio. This one is not a race — it is deterministic, and worse than "arbitrary".

window-manager.ts:3483   isTileableInCurrentMode = !this.isTiled || shouldTile(window)
                         floating short-circuits → every new window becomes activeWindowId

window-manager.ts:3601   nextFocus = tileableWindows()[ Math.min(index, len-1) ]
                         index is taken from the FULL windows array…
                         …but used to index the FILTERED tileable array

A just-opened dialog sits at the end of this.windows, and floating workspaces never reorder, so index >= tileableWindows().length always holds, the clamp always fires, and the pick is always the newest surviving tileable window. Reliably wrong rather than randomly wrong.

Ruled out from the logs Keeper does not xdg-activate the Vault after the prompt closes. Across all three captured runs the only activation is for the dialog itself, so no part of this is the client's doing — the close-path pick is the whole cause.

Why the obvious fix doesn't work

The config already keeps an MRU map, lastFocusedAt, written by recordFocus. Ranking survivors by it looks like a two-line fix. It isn't, because onOpen calls window.focus() unconditionally, and that round-trips through onFocus into recordFocus. The map records most recently opened or focused, not where you were working:

09:33:40.70  rio 0x10 opens                        → recordFocus(rio)   = 09:33:40
09:33:59.40  0x11 opens "Keeper Password Manager"
09:34:01.05  retitles "Keeper® Vault — …"           → recordFocus(vault) = 09:33:59

The SSH request launches Keeper, so the Vault stamps itself seconds before the prompt appears and outranks rio. MRU would select the Vault — precisely the window being complained about — and each occurrence re-stamps it, so it never recovers on its own.

The fix therefore needs a signal that distinguishes the user focused this from this window focused itself on open: stash the pre-burst focus holder at onOpen, or suppress the MRU stamp for a window's own initial self-focus.

C · The dock inherits the same poison

lastFocusedAt exists to let the dock pick "the most recently used window of an app" on left-click. Since every window stamps itself at open, that feature has the same defect: a newly-opened window of an app always outranks the one actually being used. Nothing has gone visibly wrong yet, but it is the same bug wearing different clothes, and whatever signal fixes B should fix the dock too.

What KWin does instead

Worth the comparison — it named the gap precisely. The difference isn't that KDE raises new windows harder; it's that KWin has arbitration where ShojiWM has none.

KWinShojiWM
Stacking constrained separately from focusonFocus raises unconditionally, so any stray focus edge rewrites the stack
mayActivate validates the activation token against lastInteractionSerialEvery activation request is obeyed; nothing is checked
Denied activation goes on the attention chain and the taskbar highlights itNo such channel — refusing would mean losing the window
On close: transient parent, then an MRU focus chainPositional index into a filtered array

The honest limit: KWin's transient-ancestry rules would not have saved us here either. The two Keeper toplevels are separate clients with no parent relationship, so set_parent is protocol-impossible and every parentage-based rule has nothing to work with. That attention-channel row is the load-bearing one — build the "denied but visible" path before any denial rule, or a refused activation just loses the window a different way.

Draft issue text

A window focus queued from the config's onOpen is recorded in pending_initial_focus_window_ids and replayed later, when the window first reaches a rendered frame. apply_pending_initial_focus_for_window (input.rs) applies that replay unconditionally — it removes the id from the set and calls focus_window with no check that the request is still current. The drain vector is filled inside the z-descending render walk and consumed last-write-wins, so the winner is decided by client paint latency rather than by focus intent.

An application that maps a blank host toplevel and then its real window a frame later will therefore have the host steal focus back from the window that was activated after it, including from an explicit xdg-activation. Separately, a focus request aimed at a not-yet-ready window is discarded rather than replayed (should_defer_initial_keyboard_focus), so the explicit activation buys nothing.

Worth raising even without a patch attached — the two behaviours are independently defensible on their own and only combine badly. A fix needs a policy call that is properly his to make.
